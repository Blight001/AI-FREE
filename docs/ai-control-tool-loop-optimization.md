# AI 控制工具循环优化方案

## 决策

先实施**结构化模型请求裁剪**，用同一套验收场景判断是否需要在侧栏加入**页面执行状态投影**和**特定空转检测**。三个阶段各自交付和验证。优先把改动集中在主进程侧栏聊天链路。是否扩大到 MCP 协议、自动化执行器或 Chromium 输入能力，由各自的独立问题和验收决定。

优化的目标是提高任务完成率，同时控制延迟、请求体积、重复副作用和维护成本。能安全定位时继续做用户要求的事。证据不足时给出具体卡点和可行的恢复方式。业务结果有疑问时优先读取实际状态。

## 已知事实与待验证假设

- 内置模型的流式响应已发送完整 `result` 事件后，旧客户端仍等待 HTTP 响应结束。若服务端或中间层延迟关流，已收到的下一步工具参数无法及时交给执行器。本地回放让响应不主动结束，旧版等到超时；修复后客户端消费完整结果即继续，并关闭仍未结束的响应。分片、停止和缺少完整事件时的错误处理仍保留。
- 开发模式首页日志可筛选 `AIControlTiming`。按 `round` 查看 `contextMs`（整理上下文）、`modelRequestMs`（发出模型请求到收到结果，含传输与远端等待）、`dispatchPrepMs`（解析并准备派发）和 `toolBatchMs`（执行整批工具）。日志只含阶段、计数和耗时，不写入对话、参数、回执或凭据。此修复不减少依赖上一步结果的模型往返，也不改变自定义 API 的非流式响应方式。

- 画圆原对话记录了 31 次成功的工具调用。其中十组重复「列标签页、接管、观察」，全程没有 `browser_action`。第一次观察已经返回了原生「圆形」按钮。复用这份真实回执做本地回放，单条文本裁剪破坏了 JSON 并移除了按钮。可见控制能力与模型实际收到的信息之间存在差异。
- 用约 51 KB 的模拟截图回放时，整轮预算挤掉了标签确认和接管回执。只提高总预算或只保留一个按钮，分别仍会留下其中一类缺失。原截图字节和远端实际推理过程没有保存，因而无法确认原对话的每次重复由哪一种缺失触发。
- 当前模型请求有消息窗口和字符预算两道裁剪，还受传输体积限制。截图附件可能影响历史选择。`pageToken` 和 `expectedPageToken` 已负责文档身份校验。现有工作流也已经约定通过读回处理未知结果。复用这些边界可以减少新增状态和恢复规则。 [消息窗口](../src/app/backend/lib/ai-control-message-window.js) · [上下文预算](../src/app/backend/lib/ai-control-context-budget.js) · [页面绑定](../src/app/backend/features/ai-chat/chat-browser-target.js) · [工作流行为](browser-workflow-modes.md)

## 阶段一 · 保留可执行的观察结果

- 只处理发送给模型的副本。以观察结果中的完整元素为裁剪单位，优先保留结果状态、错误码、截断标记、视口和坐标系、观察 ID，以及模型后续定位所需的 `ref`、角色、名称或定位器。保留工具端已经应用的查询条件。空间不足时按项减少，标明省略数量和原因，引导模型用已有的 `keyword`、`tags`、区域等过滤重查。下载、上传、等待等结果至少保留与后续动作有关的错误和回执。结果无法完整放入时使用可解析的部分结果，避免任意截断 JSON 字符串。
- 集中评估用户目标、近期工具调用及其配对回执、工具定义、文本和图片的总成本。模型估算上下文和传输请求体是两个不同约束，两者都要检查。图片单独分配子预算，并计入最终请求体上限。优先发送最近且与当前任务有关的图片。缩放或裁切时明确原视口、裁切偏移及坐标换算。无法保证映射时，模型需用结构化定位或重新观察。视觉模型无法读取图片时，依赖像素的任务要如实说明限制。
- 遇到超预算时依次缩减旧图、旧历史和冗余字段，保留当前用户请求及有效的工具调用配对。若最低必要输入仍无法发送，明确报出原因。阶段一先用当前工具交付可行的最小版本。截图解码、缩放和引用服务各自需要性能或产品数据支持才纳入，且优先使用已有能力。

### 阶段一实施记录

- 请求组装保留当前任务和配对的近期工具回执。大回执以合法 JSON 发送，`_context_omitted` 表示内容经过裁剪，`_context_items_omitted` 记录省略的元素数。模型可使用保留的观察 ID 和完整定位值继续动作。
- 默认文本预算为 60,000 字符，工具图像另有 96,000 字符，预算包含对应的消息封装。用户主动附加的内容沿用工作区输入限额，并与工具定义一起计入模型上下文估算。超限图像打上 `image_omitted_reason: "context_budget"`，历史留存原始工具回执。
- 在真实 Chromium Fork 上通过本地模型回放。使用 42 个工具栏按钮和超预算的真实截图，验证模型请求中仍有标签、接管和圆形按钮。只点击和拖拽各一次，从实际渲染的 SVG 圆读回数量 1、直径 96。可用 `node test/acceptance/fixtures/ai-control-interaction/native-model-smoke.js` 复测。
- 真实模型的重复调用率仍需独立采样。回放已满足阶段一的执行目标，阶段二和阶段三的启用条件仍分别是复现准备状态丢失和确认持续空转。

## 阶段二 · 让模型知道页面操作进行到哪里

阶段一通过后，如果同样的任务仍会因丢失准备步骤而重来，再加主进程内存中的简短投影。投影从现有运行事实导出，每次模型请求最多发送一份。内容限于当前连接、最近验证的目标文档、最近得知的接管结果、可用观察及尚待核验的动作。信息未核验时明确标记为未知。

以现有连接、文档身份和观察有效性为准。用户切页、同地址刷新、浏览器断开或接管释放时，相关事实失效。执行动作前继续走已有页面守卫。投影在当前运行结束后释放。读取历史来继续任务时重新识别实时页。用户在运行中插入新要求时，重新评估任务目标和进展，已派发动作的待核验状态继续保留。并发对话分别持有投影，实际页面权限由现有运行时判断。

投影只描述工具可证实的运行事实。页面文字、模型对页面的解读和截图内容继续作为数据，通过现有消息边界传递。诊断与模型投影只使用必要字段。内部文档令牌继续由主进程和运行时持有。 [对话执行](../src/app/backend/features/ai-chat/chat-conversation-runner.js) · [页面绑定](../src/app/backend/features/ai-chat/chat-browser-target.js)

## 阶段三 · 对可确认的空转采取有限干预

- 先在本地夹具中记录检查器本来会在哪一步触发，执行仍按原路径运行。第一类检测只覆盖已复现的模式。对同一连接和同一文档，两次完成「列标签、接管、泛观察」，中间没有输入动作、显式等待或得到新的可用目标，才给模型一次具体纠偏，例如按名称或区域查询并使用返回的定位信息。下一次又开始相同准备序列时暂停当前任务，并报告已验证的步骤和剩余卡点。两次是画圆夹具的试验阈值，以上线前的误停回放结果为准。首版检测覆盖已复现的准备序列，交替执行多种动作的长循环仍需用新的回放证据评估。
- 连接名称和 ID 对应同一浏览器。每轮变化的 `observationId`、换一个泛观察 `limit`、时钟或动画闪动都不足以证明进展。更窄的查询真实返回新控件，或显式等待的条件达成，可以证明进展。缺少稳定的比较依据时，仅记录诊断。用户指定的多项动作、合法等待、分页、切页和刷新使用各自已有的反馈与终止条件。
- 暂停消息要区分「还未执行鼠标动作」「已发送动作，结果待核验」「业务结果已核验」。结果未知时接入原有读回契约。上传选中文件、站点收到文件和返回成功回执分别确认。已有动作回执丢失时，恢复先检查实际业务状态。继续使用现有停止入口和工具时间线。优先走已有终止与清理路径。

## 二阶与三阶影响

| 影响面 | 二阶影响 | 三阶影响与控制措施 |
| --- | --- | --- |
| 模型上下文与兼容 | 缩小回执能更快送入下一轮。模型也可能因缺字段增加定向查询，截断行为会影响不同模型的工具使用。 | 用同一套回放送入自定义 OpenAI 兼容链路和内置模型链路，核对最终发出的消息角色、工具配对和结果。按可观测能力处理回执，避免为模型型号逐个加分支。 |
| Chromium、下载上传和自动化 | 更充分的状态让模型更快发出输入动作。错误关联的旧坐标或旧回执也会更快影响真实页面。 | 保留文档、观察、文件身份与上传确认校验。先在侧栏请求边界验证，外部 MCP 和自动化卡片继续使用既有契约。缺少真实业务证据时，回执明确停留在「已派发」或「待核验」。 |
| 用户的停止、续接与信任 | 及时说明卡点可以减少用户反复插入「怎么回事」。若中途暂停后重复提交同一句，可能与之前的未知动作重叠。 | 新一轮先读取目标状态。界面说明哪些动作已经派发，允许用户决定下一步。刷新和切页由系统描述具体差异，避免用户把「暂停」理解为已撤回动作。 |
| 时延、流量与资源 | 少传旧图能降低网络耗时。频繁裁图、附加浏览器查询或重复遍历历史可能增加主进程 CPU、内存和首个动作延迟。 | 测量每轮体积、模型往返、首个有效动作耗时及长会话峰值内存。优先重用工具现有回执来更新投影。若引入图像处理，按实际需求启用并限制峰值内存。 |
| 诊断与隐私 | 更细的失败分类方便定位「工具成功、任务未推进」。完整记录页面文字和截图会增加数据保留和维护负担。 | 使用现有本地诊断记录次数、耗时、体积、错误码和裁剪原因。正文、截图、凭据、页面令牌和授权头由既有保密边界处理，诊断字段采用白名单。 |
| 长期维护 | 增加投影、进展规则和降级路径后，后续工具可能需要同步维护多处规则。 | 页面状态由现有页面绑定负责，模型输入裁剪集中在请求组装，策略只消费少量已验证的公开结果。每阶段采用独立变更便于回退。先验收阶段一，后续阶段只在数据证明有剩余问题时启用。 |

## 验收与上线判断

| 场景 | 验收观察点 |
| --- | --- |
| 有原生形状工具的画布 | 本地夹具使用含大量工具栏项的页面和超预算截图。截获最终模型请求，验证原始任务、合法工具 JSON、有效定位和接管依据。随后点击圆形、拖拽一次，夹具按实际图形类型或像素几何验证圆形及数量。回放验证输入边界，再分别用模型替身和可用的真实模型做行为验收。 |
| 只有自由画笔的画布 | 缺少连续指针轨迹能力时给出明确限制。一次直线拖拽或像素发生变化均不足以证明画出了圆。 |
| 同 URL 刷新、手动切页、接管丢失、两个会话交错 | 失效的观察和接管投影无法授权输入。重新确认页面后使用新观察继续。检查同名浏览器、索引变化和对话插入。 |
| 慢页面、分页、合法重复操作与动画 | 合法任务能继续。仅变动的观察 ID、动画或时钟无法让已识别的空转永久延续。 |
| 输入、下载或上传已派发且回执丢失 | 核对输入事件计数、下载文件或站点收件数，验证无额外副作用。投影及界面保留结果未知，读回成功后才更新结果。 |
| 不支持视觉、图片超传输上限、停止与历史恢复 | 文本可完成的任务继续，必须依赖图像的任务说明缺失证据。验证最小必要输入超限诊断、及时停止、重开后的实时校验和正常的历史展示。 |

门槛分两组。硬指标是工具调用配对和 JSON 有效、旧文档动作被拒绝、未知结果无重复副作用、画圆夹具实测图形正确。体验指标以现有版本在同一夹具的复测为基线，比较任务成功率、空转误停、成功动作前调用数、端到端耗时、请求体积和长会话内存。若仅阶段一已满足目标，暂缓增加执行状态投影和拦截规则。若检测误停合法任务，保留诊断并回退拦截。

实施后依次运行定向回归、`npm run guardrails`、`npm run verify`、`npm run test:acceptance`。真实 Chromium 用例再运行 `npm run accept:chromium-phase3`，同时记录相关专项用例及独立环境失败。运行入口涉及生成态时通过 `npm run prepare:source` 构建。触及打包资源布局时再运行 Windows 构建和 packaged runtime 校验。现有本地浏览器与侧栏夹具可作为增量测试入口。 [交互验收夹具](ai-control-interaction-acceptance.md)
